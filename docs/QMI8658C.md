# QMI8658C acquisition contract

TM-003 owns the QMI8658C register driver and deterministic sample acquisition only. Orientation estimation, neutral handling, cursor mapping, USB HID, and touch buttons are intentionally outside this module.

## Bus and identity

The ESP32-S3 adapter uses the board contract's GPIO11 (SDA) and GPIO12 (SCL) on I2C port 0 at 400 kHz. The QMI8658C rev. 0.9 datasheet permits I2C SCL up to 400 kHz.

The datasheet documents the 7-bit address as:

- `0x6A` when SA0 is pulled high or left unconnected; and
- `0x6B` when SA0 is pulled low.

This corrects the address-polarity wording in the original programme material. The driver does not depend on the board strap: it reads `WHO_AM_I` (`0x00`) at `0x6A` first, then falls back to `0x6B` for a NACK or identity mismatch. A valid QMI8658C must return `0x05`.

I2C transactions use a 20 ms target-side timeout. NACK and timeout are kept distinct at the bus seam. Short successful transfers are also rejected by the portable driver rather than being treated as valid register data.

## Reset and configuration

TM-003 uses the following deterministic configuration from the QMI8658C rev. 0.9 register definitions:

| Step | Register | Value | Meaning |
| --- | --- | --- | --- |
| reset | `RESET` `0x60` | `0xB0` | soft reset |
| serial interface | `CTRL1` `0x02` | `0x40` | auto-increment enabled, little-endian data, oscillator enabled |
| disable before configuration | `CTRL7` `0x08` | `0x00` | accelerometer and gyroscope disabled |
| accelerometer | `CTRL2` `0x03` | `0x15` | ±4 g, ODR code `0101` |
| gyroscope | `CTRL3` `0x04` | `0x55` | ±512 dps, ODR code `0101` |
| digital LPFs | `CTRL5` `0x06` | `0x00` | accelerometer/gyroscope optional LPFs disabled |
| enable | `CTRL7` `0x08` | `0x03` | accelerometer and gyroscope enabled |

ODR code `0101` is **235 Hz in 6DOF mode**. The same accelerometer code is 250 Hz only when the accelerometer operates alone. Since TiltMouse enables both accelerometer and gyroscope, 235 Hz is the documented operating rate nearest the programme's approximately 250 Hz estimator target; the implementation does not relabel it as 250 Hz.

The ±4 g accelerometer scale is 8192 LSB/g. The ±512 dps gyroscope scale is 64 LSB/dps.

The driver waits 200 ms after soft reset before re-verifying identity, then waits 80 ms after enabling both sensors before permitting acquisition. These waits conservatively cover the datasheet's sensor start-up timing. The waits live behind the bus abstraction, so host tests remain deterministic.

## Sample contract

`qmi8658_read_sample()` first requires both accelerometer and gyroscope data-available flags in `STATUS0`. It then performs one auto-incrementing burst beginning at `TIMESTAMP_L` and covering timestamp, temperature, accelerometer, and gyroscope output registers.

A successful `qmi8658_sample_t` contains:

- `host_time_us`: monotonic host time captured after the successful register burst;
- `sensor_timestamp`: the QMI8658C 24-bit circular sample timestamp/count, zero-extended to `uint32_t`;
- `accel_g[3]`: X, Y, Z acceleration in **g**;
- `gyro_dps[3]`: X, Y, Z angular rate in **degrees per second**.

Axes remain in the QMI8658C native right-handed sensor frame. TM-003 performs no board-orientation transform and no cursor mapping; TM-004 owns that behavior.

On `NO_DATA`, NACK, timeout, short read, or another acquisition error, the caller-provided sample is left unchanged. Failed or partial I2C activity therefore cannot silently become a plausible new sample.

## Polling decision

INT1 (GPIO10) and INT2 (GPIO13) remain unused in TM-003. The portable API exposes explicit data-ready status and timestamps, so later integration can poll at the intended fixed acquisition cadence without coupling this driver to a particular scheduler. Interrupt-driven acquisition can be considered later if physical timing evidence shows a need.

## Evidence boundary

Host tests establish register ordering, address fallback, exact configuration bytes, scaling/decoding, and failure propagation against a deterministic mock bus. CI's ESP32-S3 build establishes compatibility with the pinned ESP-IDF API. Neither is physical proof that a particular board's IMU wiring, pull-ups, axes, or timing behave as expected; that remains target-hardware evidence for the later physical acceptance work.
